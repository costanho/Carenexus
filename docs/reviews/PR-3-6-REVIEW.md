## PR #6: UI/UX audit: contrast, phone-width web navigation and layout, accessibility

PR #6 is mostly a mechanical palette swap to darker, AA-contrast shades across 76 files, plus a new phone-width NavDrawer for the doctor and caregiver web dashboards, wrapping page headers and stat cards, tablist fixes and a growing mobile composer. Quality is good: I found no crashes, state bugs or desktop layout regressions, and the follow-up commit already covered the drawer focus trap and the dark surfaces (navy hero, doctor sidebar, call room). Two issues remain at HEAD: the patient web drawer was never moved onto NavDrawer despite the PR saying all three roles share it, and the palette swap made the Monitor and Critical health dots nearly the same colour where the dot is the only cue. Nothing was run; this is from reading the diff and the files at HEAD.

### 6.1 Medium (confirmed, web): `frontend/src/components/web/direct/patient-dashboard-web.tsx:238`

The patient web dashboard still uses its own phone-width drawer (a bare absolutely positioned sidebar) instead of the new NavDrawer, so it has no backdrop, no Escape handling, no focus move or trap and no focus return. docs/ui-ux/AUDIT.md and the nav-drawer.tsx docstring both state that all three roles now share the backdrop/Close/Escape pattern, which is only true for doctor and caregiver.

**Failure scenario.** Patient at 390 px wide (or a desktop keyboard user zoomed to 400%, which gives the same layout) presses 'Open menu'. Focus stays on the hamburger; because the drawer is rendered before the main area in the DOM, Tab moves forward into page content that is hidden underneath the drawer, and the drawer items are reachable only with Shift+Tab. Escape does nothing. Clicking the visible strip of page to the right of the drawer does not close it and instead activates whatever is there (bell, Sign out in the top bar, page cards). The same actions on the doctor and caregiver dashboards close the drawer or stay trapped inside it.

**Suggested fix.** Render the patient sidebar through NavDrawer as the other two dashboards do: <NavDrawer open={isSmall && drawerOpen} onClose={() => setDrawerOpen(false)}><PatientLeftSidebar collapsed={false} activeKey={activeKey} onNavigate={handleNavigate} /></NavDrawer>. Drop the styles.drawerOverlay block and the sidebar's own onClose button (NavDrawer supplies Close menu), and add the same effect that closes the drawer when width goes above 768.

**Verifier.** Traced at HEAD. frontend/src/components/web/direct/patient-dashboard-web.tsx:238-247 renders the phone-width drawer as a bare `<View style={styles.drawerOverlay}>` (styles at 286-297: position absolute, top/left/bottom only, no right, no backdrop) wrapping PatientLeftSidebar (width 260, patient-left-sidebar.tsx:220). NavDrawer is imported only by doctor-dashboard-web.tsx:151 and proxy/patient-proxy-dashboard-web.tsx:110; the patient dashboard does not use it. patient-left-sidebar.tsx has only a 'Close menu' button (line 127-128) and no keydown/Escape/focus code; the dashboard has no key handler either. So at <768 px: no backdrop (the ~130 px strip of page right of the drawer at 390 px stays live and clickable, including top-bar controls), Escape does nothing, focus stays on the 'Open menu' button and is not trapped or returned. The drawer is rendered before `main` in the DOM (line 238 vs 249), so forward Tab from the hamburger goes into page content behind the drawer. docs/ui-ux/AUDIT.md:53 ('Below 768 px all three roles now use the same pattern ... with a backdrop, Close menu and Escape') and the nav-drawer.tsx docstring (lines 12-19, 'same pattern as the patient dashboard') are therefore inaccurate for the patient role. Not fully blocking (a visible Close menu button exists and nav items are clickable), so medium severity is fair.

## PR #5: Mobile: fix post-merge review findings and make the draft store crash-safe

PR #5 fixes seven small mobile UI review findings and rewrites the native draft/outbox store (storage.native.ts) as a two-slot, pointer-switched index over SecureStore with reserved ids, a persisted trash list and retry. I traced the store's save, load, migration, locked-keychain and sign-out paths against the installed expo-secure-store 56.0.4 and React Native 0.85.3 sources and found no atomicity, corruption-recovery, write-race or cross-account defect at HEAD; the UI fixes also hold. The two findings below are both low severity; note also that the crash-injection harness the PR cites is not committed, so about 300 lines of crash-safety logic have no regression test in the repo, and Android was never run.

### 5.1 Low (confirmed, mobile): `frontend/src/lib/communications/storage.native.ts:379`

On Android the store's write pass is started by setTimeout(0), which does not fire while the app is in the background, so the draft save on leaving the foreground never reaches the Keystore until the app is resumed.

**Failure scenario.** Android user types in a conversation and, within 400 ms of the last keystroke, the app is paused (Home, app switch, incoming call). use-draft.ts:40 flushes on the AppState change and nativeStorage.setItem updates memory, but runFlush() only queues setTimeout(..., 0). In the installed RN 0.85.3, TimerManager::createTimer sends every timer (delay 0 included) to JavaTimerManager.createTimer, and its frame callback returns early while isPaused (JavaTimerManager.kt:72-76, 291). If the process is then killed in the background, that text is lost, which is the exact case the comment at use-draft.ts:38 says is covered. The same applies to any store change made while paused: an outbox removal when a send is confirmed after backgrounding (the delivered message reappears as 'Message not sent' on next launch until the thread refetch settles it), a session-expiry clear (the previous user's drafts stay on disk until the next user opens Messages), and the retry timers. iOS is unaffected (RCTTiming runs timers in the background).

**Suggested fix.** In runFlush, coalesce with a microtask instead of a timer (queueMicrotask or Promise.resolve().then), which still batches a synchronous burst of setItem/removeItem calls but runs while the host is paused. Keep the AppState 'active' handler for retries. Verify on an Android emulator by backgrounding within 400 ms of typing and force-stopping the app.

**Verifier.** Code is at HEAD as described. frontend/src/hooks/use-draft.ts:40 flushes on AppState != 'active' -> saveDraft -> nativeStorage.setItem (storage.native.ts:403-407) -> schedule -> runFlush, which only queues setTimeout(..., 0) at storage.native.ts:379; no SecureStore write happens synchronously. In the installed react-native 0.85.3, TimerManager::createTimer (ReactCommon/react/runtime/TimerManager.cpp:102) always calls platformTimerRegistry_->createTimer, which on Android is JavaTimerManager.createTimer (delay 0 is not special-cased there; only the unused createAndMaybeCallTimer path fires immediately). JavaTimerManager.onHostPause sets isPaused and removes the frame callback (JavaTimerManager.kt:72-76, 140-144) and TimerFrameCallback.doFrame returns early while paused with no headless task (line ~291). AppStateModule emits 'background' from the same onHostPause, so by the time JS handles it the timer cannot fire until onHostResume. So the last keystrokes (and any other store change made while paused: outbox removal after a confirmed send, sign-out clears, the scheduleRetry timers at line 372) stay memory-only and are lost if the process is killed in the background, which is the exact case the comment at use-draft.ts:38 claims to cover. No other guard (the only AppState listener in storage.native.ts:395 acts on 'active' only). Android-only, low severity. The cited path 'use-draft.ts:40' is frontend/src/hooks/use-draft.ts:40.

### 5.2 Low (confirmed, mobile): `frontend/src/lib/communications/storage.native.ts:104`

Orphan detection and deletion stop at MAX_PROBE (64) chunks, so a value larger than 38,400 characters that is left uncommitted by a kill keeps its chunks 64+ in the keychain forever, where sign-out can never clear them.

**Failure scenario.** A thread's outbox is one JSON value holding every unsent message (outbox.ts:60), so ten failed 4000-character messages is about 67 chunks. The app is killed after the data chunks are written but before the pointer switches. On the next start readStoreSync finds the reserved id via countChunksSync, which caps at 64 (line 104), and records trash(id, 64). deleteChunks(base, 64) starts with n = 64, skips the probe loop because n < MAX_PROBE is false (lines 122-123), deletes and verifies chunks 0-63, and drops the id from the trash. Chunks 64-66, containing message text, are now named by nothing and cannot be listed, which breaks the invariant stated at lines 21-29. The same cap applies to probeIds (line 143) and the reserved-id scan (line 213). Paths that know the real count (normal replace, failed write in the same run) are not affected.

**Suggested fix.** Make the probe unbounded for deletion: in deleteChunks, keep probing `${base}.${n}` until the first missing chunk regardless of MAX_PROBE, and let countChunksSync do the same (or return a sentinel meaning 'at least MAX_PROBE' that forces a full probe on delete). Alternatively cap what is stored (reject or split values above MAX_PROBE * CHUNK_UNITS, e.g. limit the number of unsent messages kept per thread).

**Verifier.** Traced at HEAD. writeChunks (storage.native.ts:109-111) writes every part with no cap, but countChunksSync caps at MAX_PROBE=64 (line 104). After a kill between the data writes and the pointer switch (line 316), readStoreSync finds the uncommitted id via the reserved scan (lines 211-214) or probeIds (line 143) and records trash(id, 64) for a value that actually has >64 chunks. pass() then calls deleteChunks(base, 64) (line 335): n starts at 64, the probe loop at line 123 is skipped because n < MAX_PROBE is false, chunks 0-63 are deleted and verified, and trash.delete(tid) drops the id. Chunks 64+ (message text) are named by no index and cannot be listed, so sign-out can never clear them, contradicting the invariant at lines 21-29. Reachability: outbox.ts:60 stores a thread's whole outbox as one JSON value with no cap on the number of items (use-thread-messages.ts:278 appends each send; failed ones stay), and MAX_MESSAGE_LENGTH is 4000, so ~10 failed max-length messages in one thread exceed 38,400 code units. Requires that plus a process kill during the write of chunks 65+ / index / pointer, so it is rare; low severity is appropriate. Paths with the true count (normal replace via entries, same-run failure at lines 304/323, line 203 Math.max) are unaffected, as the finding says.

## PR #4: Mobile: messaging, notifications and caregiver consent

PR #4 ports messaging, notifications and caregiver consent to the Expo mobile app by adding mobile screens (inbox, thread view, composer, bell, Message buttons) on top of the shared hooks and lib/communications from PR #2, plus a SecureStore-backed draft/outbox store and AppState-aware polling. The mobile screens themselves are careful (back handling, 403/404 states, outbox retry with a stable clientMessageId, per-user draft keys) and the frontend/backend contract matches. The real defects are in the shared data-flow hooks the mobile screens depend on: one high-severity cursor bug that silently skips incoming messages in an open thread, one inbox pagination bug, and three low-severity inconsistencies. Review was by code reading only; nothing was run.

PR #4 brings messaging, notifications and the patient's caregiver-consent screen to the Expo mobile app; it is frontend-only (no backend file changed), reusing the web hooks and several web components. Through the security/consent lens the work is solid: the backend re-checks consent on every request, the 403 state hides loaded messages, drafts/outbox/unread counts are per-user and cleared on sign-out, the secure-store adapter handles locked-keychain and crash cases, and no PHI is logged. I found no critical or high defects; three lower-severity issues remain at HEAD: a role-casing mismatch that hides "Leave conversation" for doctors and caregivers, no way for a patient to decline a pending caregiver request despite the documented approve/deny, and a caregiver permission grid that ignores the access level.

### 4.1 High (confirmed, shared): `frontend/src/hooks/use-thread-messages.ts:256`

A confirmed own send is merged into the message list and thereby advances the poll cursor, so any incoming message with an id between the last poll and the user's own message is never fetched, and it is marked read. post() calls absorb([confirmed]) (line 256); poll() then uses the newest id in the list as `after` (lines 188-192), and absorb() also calls markRead(newest).

**Failure scenario.** Patient has the thread open and last polled at message id 100. The doctor sends id 101. Two seconds later, before the next 5 s poll, the patient sends a message that is stored as id 102. The POST response is absorbed, so the list is [..100, 102], and markRead(102) marks the doctor's notification read (the server also sets last_read=102 on send). Every later poll asks for after=102, so message 101 never appears in the open conversation and there is no unread badge or notification for it anywhere. It only shows up if the user leaves and reopens the thread. Same root cause: if the initial load failed and the user sends, the list becomes just [own message], hasOlder stays false, and the whole earlier history is hidden with no 'Load earlier messages' button.

**Suggested fix.** Keep a separate contiguous server cursor (highest id received from list/poll responses) and use it for `after` and for markRead; do not let a POST-confirmed message move it. Simplest: in post().then, run poll() (which fetches after the old newest id and will include both the other party's message and the own one) instead of absorb([confirmed]), or absorb the confirmed message only after such a poll.

**Verifier.** Traced at HEAD. post() calls absorb([confirmed]) (use-thread-messages.ts:256), which merges the own message into messagesRef; poll() takes the last id of that list as `after` (lines 188-192) and the backend returns only ids strictly greater (MessageService.listMessages -> findVisibleAfter). So with list [..100], doctor message 101 stored, own send stored as 102 before the next 5 s tick, every later poll asks after=102 and 101 is never fetched. absorb() also calls markRead(merged) -> POST read 102, and NotificationRepository.markThreadReadUpTo marks every notification with messageId <= 102 read; sendMessage already set last_read=102 (MessageService.java:156), so the thread unread count is 0 too. No gap detection exists: the outbox subscriber's extra poll (line 111) is skipped because the message is already in messagesRef, and neither thread view reloads on send. The message only reappears on reopening the thread (fresh newest-30 load). Secondary case (failed initial load then send) is also reachable since the composer stays enabled, but it needs the send to land before the first successful cursor-less poll. Note: this hook was not changed by PR #4 itself; PR #4's MobileThreadView uses it (mobile-thread-view.tsx:50).

### 4.2 Medium (confirmed, shared): `frontend/src/hooks/use-threads.ts:51`

The first-page refresh keeps `prev.slice(PAGE_SIZE)` as 'rows from later pages', so once more than one page is loaded, the conversation pushed from position 20 to 21 by a new or newly active thread is dropped from the list and never re-fetched.

**Failure scenario.** A doctor with 40 conversations scrolls the mobile inbox (FlatList onEndReached loads page 2, pagesLoaded=2). A message arrives in a new thread or in a thread from page 2. The 15 s poll (or the refetch after Back or after sending) returns a first page of [moved thread, t1..t19]; rest = prev.slice(20) = t21..t40, so t20 is in neither part. hasMore is false (pagesLoaded 2 >= totalPages 2), so t20 stays missing from the inbox until it gets new activity or the tab/filter is switched.

**Suggested fix.** On refresh, re-fetch every loaded page (pages 0..pagesLoaded-1, or one request with size = pagesLoaded * PAGE_SIZE where the 50 cap allows) and replace the list; or merge by id over the whole previous list instead of slicing by index, and reset pagesLoaded when the merged length no longer matches.

**Verifier.** use-threads.ts:51 keeps `prev.slice(PAGE_SIZE)` minus ids in the fresh first page. With prev = t1..t40 (pagesLoaded=2, reached via FlatList onEndReached in mobile-thread-list.tsx:89 or the web Load more button) and a poll returning [t30, t1..t19] (server order is lastMessageAt DESC, MessageThreadRepository:39), rest = t21..t40 minus t30, so t20 (old index 19) is in neither part. The next refetch repeats the same result (slice(20) of the 39-row list still starts at t21). hasMore = pagesLoaded < totalPages = false, and loadMore would in any case fetch page index 2, never page 1 again. t20 stays hidden until the filter/tab changes or it gets new activity. Only the local bump() path (own send) avoids it; incoming activity and new threads do not. Hook predates PR #4 but drives PR #4's mobile inbox.

### 4.4 Low (confirmed, backend): `backend/carenexus-api/src/main/java/com/carenexus/api/communications/service/MessageService.java:156`

### 4.6 Low (confirmed, shared): `frontend/src/components/web/messages/new-conversation.tsx:154`

The first message of a new conversation bypasses the outbox: when its POST fails, the text is saved as a plain thread draft, so the original clientMessageId and the urgent flag are lost.

**Failure scenario.** On a poor mobile connection the conversation is created, and the first-message POST is stored by the server but the response times out (15 s). The app shows 'Message not sent... Your text is kept in the message box' and opens the thread, where the history already contains the message and the composer holds the same text. Sending it again uses a new clientMessageId, so the care team receives the message twice. If the POST really did fail and the message had been marked urgent, the composer's urgent switch is back to off, so the re-send goes out as a normal message.

**Suggested fix.** On failure, put the message into the thread's outbox as a failed LocalMessage with the same clientMessageId and urgent flag (updateOutbox(threadOutboxKey(mySystemId, thread.threadId), ...)) instead of saving a draft, so the thread view shows it with Retry / Discard and the server de-duplicates a retry.

**Verifier.** new-conversation.tsx:149-156 posts the first message with sendMessage directly (not through the outbox) and on any error stores only trimmedBody with saveDraft(threadDraftKey(...)) and shows 'Message not sent ... File predates PR #4 but is the form PR #4's mobile screen renders.

### 4.7 Low (confirmed, mobile): `frontend/src/components/web/direct/patient/patient-web-caregiver-access.tsx:461`

The patient's caregiver-access screen (wrapped for mobile by patient-mobile-caregiver-access.tsx and described in the PR, docs and messaging-actions.tsx:28 as "approve / deny / revoke") offers only Approve for a pending messaging/calls request; there is no control that sends `canMessageCareTeam: false` / `canJoinCalls: false`, so a request cannot be declined.

**Failure scenario.** A caregiver's grant has canMessageCareTeam=true unapproved (requested from the web add-loved-one form). The patient opens the approval notification on the phone: the card shows "Needs your approval" with one Approve button (which approves every pending request at once), and the toggles below read "Requested, not approved" in the off position, where a tap sends `true` (approves). **Failure scenario.** (1) The caregiver clears the Phone field and taps Save. The PUT sends phone:'' and UserProfileService skips blank phones, so the call returns 200 and the editor closes as if saved, but the old number is still shown with no explanation. (2) The PUT succeeds but the GET on line 444 fails on a network blip. The catch shows "Unable to reach the server" and keeps the editor open, although the name change was already persisted.

**Suggested fix.** Use the PUT response body, as saveHealth does, instead of a second GET. Either require a phone or tell the user it cannot be removed (or support clearing it server-side).

**Verifier.** patient-proxy-mobile-profile.tsx:443 sends phone: pPhone.trim() (no required check on phone); UserProfileService:111 skips blank phones, so a cleared phone returns 200, the follow-up GET (444) restores the old number and the editor closes with no message. Lines 443-447 put the PUT and the GET in one try, so a GET failure after a successful PUT shows caregiverSaveErrorMessage ('Unable to reach the server' / save failed) and keeps the editor open although the change persisted.

### 3.16 Low (plausible, shared): `frontend/src/hooks/use-caregiver-dependents.ts:113`

When the current user fails to load, the hooks now show an error, but the Retry they expose can never succeed because useCurrentUser only loads once on mount.

**Failure scenario.** On a cold start the stored user is missing and GET /api/users/me fails on a transient network error. useCurrentUser settles on {user:null, error}. The caregiver dashboard shows ErrorState with Retry (refetchDeps / refetchActivity). Each tap bumps `tick`, the effect re-runs, finds `!user` again and sets the same error. The screen stays stuck until the app is restarted, even after the network returns. This is the C18 fix ("spins with no retry") only half done.

**Suggested fix.** Expose a refetch from useCurrentUser and call it from the hooks' refetch when user is null, or fetch /api/caregiver/dependents without waiting on the user, since the caregiver comes from the JWT.

**Verifier.** The dead-end is real in code: use-current-user.ts:49-63 loads once with an empty dependency array and exposes no refetch, and use-caregiver-dependents.ts:110-115 re-sets the same error on every tick while user is null, so Retry cannot recover. Reaching it requires the stored user to be missing or unreadable while the session is still valid AND GET /api/users/me to fail; saveUser runs on every login and token refresh (auth.service.ts:42,50; auth.interceptor.ts:48), so the precondition is rare and I could not show a normal path to it.

### 3.17 Low (plausible, mobile): `frontend/src/components/mobile/proxy/patient/patient-proxy-mobile-profile.tsx:492`

A caregiver can permanently cut their own access (lower level, switch permissions off, set an end date) with a single Save and no confirmation.

**Failure scenario.** A caregiver created an account for an elderly parent who does not use the app. They open Your Access > Edit, tap "View Only" (or Custom with switches off, or an end date of today) and press Save. The PATCH succeeds at once. They can no longer book appointments or edit the profile, and the backend rejects any attempt to widen it again ("You can only reduce your own access"). Only the dependent can restore it, by signing in with a temporary password the caregiver may no longer have, and there is no password reset. The only warning is one line of hint text. This is a design risk rather than a logic bug.

**Suggested fix.** Before the PATCH, compare the new effective permissions and expiry with the current ones and ask for confirmation, listing what will be lost and that only the loved one can restore it.

**Verifier.** Code matches: saveAccess (patient-proxy-mobile-profile.tsx:476-510) PATCHes immediately with no confirmAction (the file never imports or calls one), the backend rejects any widening (CaregiverService ONLY_REDUCE_MESSAGE, 173-177), and the only warning is the hint at line 722 ('You can reduce your own access here. Only X can give you more.'). The finding itself calls this a design risk rather than a logic bug; behaviour is as designed by the backend rule, so it is a missing-safeguard concern, not a proven defect.
